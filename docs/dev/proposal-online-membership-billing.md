## 1. 一句话总结这次转型

从「用户在自己电脑上装一个免费/一次性买断的本地工具」，变成「一个部署在香港服务器、邀请码注册、按三级权限（游客/免费会员/充值会员）区分能力、充值靠人工记账的小规模在线站点」。比最初设想的"公开商业 SaaS"轻量很多——不需要支付渠道对接、不需要企业资质、不需要自主注册与验证码体系——但依然需要**新增账号体系、权限分级、内容后台、问答功能与 token 计量**，这部分工程量不小，只是省掉了支付合规这块最重的负担。

## 2. 现状可复用 vs 必须重做

### 2.1 可以复用（业务逻辑层，与 Electron/SQLite 解耦）

| 现有代码 | 复用程度 | 说明 |
|---|---|---|
| `src/views/**`、`src/components/**` | 高 | 纯 React 组件，UI 逻辑与 Electron 无关，port 到 Next.js/Vite Web 项目基本平移 |
| `electron/services/content-normalize.ts`、`paragraph-analysis.ts`、`parse-hash.ts` | 高 | 纯函数式业务逻辑，与存储无关 |
| `electron/ai/deepseek.ts`、`guard.ts`、`prompts.ts` | 高 | DeepSeek 调用/红线拦截逻辑可直接搬到后端服务，只是运行位置从「用户本机主进程」变成「你运营的服务器」 |
| `data/*-original.json` + `seedBuiltinContent()` 的语义 | 中高 | 内置五经内容和"稳定 ID 同步"思路保留，只是 seed 目标从本地 SQLite 换成云端共享库 |
| `electron/db/schema.ts` 的表结构设计思路 | 中 | 表关系（books/chapters/paragraphs 双键、级联删除、FTS）设计可参考，但要从 SQLite 单文件搬到支持并发多用户的数据库 |

### 2.2 必须重做或新增

| 内容 | 原因 |
|---|---|
| **整个 Electron 主进程 + IPC 层** | `electron/main`、`electron/preload`、`electron/ipc/*`、`electron/db/connection.ts` 全部基于"单机单用户单进程"假设，在线服务需要真正的后端 API 服务器 |
| **better-sqlite3 → 多用户数据库**（建议 PostgreSQL） | SQLite 是单文件、单写入者模型，撑不住多用户并发写入；且需要按 `user_id` 做行级隔离 |
| **账号体系**（邀请码注册 + 登录） | 现在完全没有账号概念；已确认不开放自主注册，改为**邀请码制**——不需要短信/邮箱验证码、不需要找回密码这类面向公众的完整流程，大幅简化 |
| **三级权限体系**（游客 / 免费会员 / 充值会员） | 全新模块，见 §4；权限判断要覆盖到"看原文"“看 AI 解读”“发起问答对话”三个能力点 |
| **Token 用量计量与钱包/余额系统** | 全新模块，需要在每次问答调用后记账并扣减余额；**充值本身走人工记账**（见 §5），不需要对接真实支付渠道 |
| **`api_credentials`（用户自配 Key UI）整个删除** | 已确认不保留用户自带 Key；AI 调用统一走平台侧 Key（存放在服务器 Secrets 管理中，绝不下发到前端），`SET-01` 这一功能面直接砍掉 |
| **内置内容 seed 机制改为后台内容管理系统** | 已确认内容由运营方后台上传管理，原来"打包 JSON、启动时幂等 seed"的思路不再适用；需要一个面向管理员的后台界面（书/章/段的创建、编辑、发布、下线）。现有 `editing.ts`（书/章/段轻量编辑：创建、改标题、合并拆分、删除）业务逻辑可直接复用改造，从"面向普通用户的桌面编辑功能"变成"面向管理员角色的后台 CRUD" |
| **AI 问答 / RAG 需要重新实现**（原 PRD 已移除的 `ask`/`rag.ts`） | 已确认要提供问答功能，这是 token 计量计费的主要来源，见 §4 |
| **`paragraph_analyses` 的重新定位** | 见 §4，这一点对计费模型影响很大 |
| **静态资源存储**（封面图等） | 现在封面图存本地文件系统，Web 版需要对象存储（如阿里云 OSS/腾讯云 COS/S3） |
| **多租户下的 FTS 全文检索** | SQLite FTS5 需替换为 Postgres `tsvector`/`pg_trgm`，或引入独立搜索服务（Meilisearch/Elasticsearch） |
| **运维/监控/限流/防刷** | 在线服务需要防止单用户刷 token、异常并发等，本地应用完全不需要考虑 |
| **管理员角色与权限体系** | 内容上传/管理需要区分"普通会员"和"内容管理员"两种角色，新增 admin 后台的鉴权与操作审计 |

## 4. 关键设计决策点（会决定计费模型是否有意义）

这是本次分析中最重要的一个发现，值得单独展开：

**现有 `paragraph_analyses`（段级白话解读）本质上是"平台内容"，不是"用户消费"。** 同一段原文 + 同一套 Prompt，生成的白话解读对所有用户都一样，现在的 `ai_cache` 设计就是按 `prompt_hash` 全局命中——这意味着：

- 如果上线后继续沿用"点一下生成白话解读"这个唯一 AI 功能，那么第一个用户触发生成后，后面所有用户看到的都是缓存结果，**平台只需为每段内容付一次 DeepSeek 的钱**，用户之间没有边际 token 消耗差异。
- 这种情况下，"按 token 使用量向用户计费"没有真实的用量可计——你没法向后面 1000 个用户中的每一个都收"token 费"，因为他们并没有各自触发新的推理。

**已确认要提供问答功能**，这正好补上了这个缺口——问答是每用户独立、不可跨用户缓存的调用（同一段原文，不同用户问不同的问题，无法复用别人的推理结果），是 token 计费天然成立的场景。据此明确两类 AI 能力的计费定位：

| AI 能力 | 性质 | 计费方式 |
|---|---|---|
| 段级白话解读（沿用现有 `paragraph_analyses`/`ai_cache`） | 平台内容，全局共享缓存 | 不单独计 token 费，算作会员费覆盖的"平台内容"，成本是运营方的固定 COGS，不转嫁到单次用户调用上 |
| 问答（新增，原 PRD 中已移除的 `ask`/RAG 接口的复活+改造） | 每用户独立、不可复用 | 按实际调用返回的 `prompt_tokens + completion_tokens` 记账，从会员的 token 余额/免费额度中扣减 |

问答功能的实现建议基于现有 `searchParagraphs`（FTS 全文检索）做检索增强（RAG）：用户提问 → 检索相关段落 → 拼接上下文交给 DeepSeek → 返回答案并按 usage 字段记账。已确认支持多轮对话，需要 `conversations`/`messages` 表存历史（同一对话的多轮追问要带上上下文）。

### 4.1 三级权限矩阵（已确认）

| 能力 | 游客（未登录/无邀请码） | 免费会员（邀请码注册，未充值） | 充值会员（余额 > 0） |
|---|---|---|---|
| 查看原文 | ✅ | ✅ | ✅ |
| 查看 AI 段级白话解读 | ❌ | ✅ | ✅ |
| 全文检索 | 待定，见 §9 | ✅ | ✅ |
| 段绑定/自由笔记 | ❌ | 待定，见 §9 | ✅ |
| 发起问答/多轮对话 | ❌ | ❌ | ✅（按 token 计量扣余额） |

- 游客能看到什么完全靠后端接口的权限校验，前端路由层面的"隐藏"没有安全意义——务必在 API 层做鉴权，不能只在前端隐藏按钮。
- "充值会员"不是一个固定套餐等级，而是"钱包余额 > 0 就能对话，余额扣完自动降级为免费会员的能力"，本质是**预付费余额网关**，不是传统意义的包月订阅分层（如果后续要加"包月无限对话"之类的套餐，是在这个模型上叠加，不冲突）。

## 5. 商业模式草案（已按人工充值模式收窄）

### 5.1 收费结构

由于**不接支付渠道，充值走线下个人转账 + 后台人工加余额**，"会员费"和"token 费"实际上都汇总成同一件事——用户的钱包余额：

1. 用户通过微信/支付宝**个人转账**（不是商户收款码）把钱转给运营方本人。
2. 管理员在后台手动给该用户账号加值，记一笔 `balance_adjustments`（金额、备注、操作人、时间）。
3. 用户对话消耗的 token 按调用返回的 `prompt_tokens + completion_tokens` 实时从余额中扣减。
4. 余额扣到 0（或低于阈值）后，该用户的"充值会员"能力自动降级为"免费会员"（不能再发起对话，但仍能看原文和 AI 解读）。

这套模式不需要：支付网关对接、Webhook 回调、退款接口、发票开具流程——因为交易发生在系统之外（个人转账），系统只需要一个**可信的人工记账入口**和**清晰的余额扣减日志**，方便日后对账（用户说"我转了 100 块怎么只剩 80"时，能查到每一笔扣减对应哪次对话）。

### 5.2 定价结构建议（示例，需结合实际 DeepSeek 成本核算）

- 直接按"每 1000 token 多少钱"定价，加成 DeepSeek 官方单价（如 1.5–3x），管理员充值时按汇率换算成对应的 token 额度记入余额。
- 因为是熟人/邀请制圈子而非公开定价页面，定价可以更灵活（比如给不同用户不同折扣），但仍建议在后台记账时把"折算成多少 token 额度"写清楚，避免日后对不上账。
- 段级白话解读继续免费（会员费/门槛之内），只有对话消耗余额——所以"充值"这件事的唯一意义就是"买对话额度"，产品页面上应该直白地这样表达，避免用户误以为充钱能解锁更多原文或解读内容。

## 6. 数据模型改动方向（不写代码，只列改动点）

| 表 | 改动 |
|---|---|
| `books`/`chapters`/`paragraphs` | 保持全局共享（内容对所有用户一致），不需要 `user_id`；新增 `status`（draft/published）、`created_by`（管理员账号）用于后台内容管理流程 |
| `paragraph_analyses`、`ai_cache` | 保持全局共享（见 §4），继续按 `prompt_hash` 命中 |
| `reading_progress`、`notes` | 新增 `user_id`，改为按 `(user_id, book_id/paragraph_id)` 维度 |
| `api_credentials` | **整表删除**：已确认不保留用户自带 Key，平台侧 Key 存于服务器 Secrets 管理，不落库、不进用户可见的任何表 |
| 新增 `users` | 会员账号：密码哈希、角色（guest 不需要账号/member/admin）、注册时使用的邀请码 |
| 新增 `invite_codes` | 邀请码：code、是否已使用/可用次数、生成人（管理员）、备注（发给谁了） |
| 新增 `wallets` | 每个 `member` 账号一条余额记录 |
| 新增 `balance_adjustments` | **人工充值记账**：金额、折算 token 额度、操作管理员、备注（如"用户微信转账 100 元，2026-07-27”）、时间——这是"充值"在系统里唯一的落地形式，没有支付网关回调 |
| 新增 `token_usage_ledger` | 每次问答调用的 prompt/completion token 数、费用、关联的会员/会话，用于余额扣减和对账 |
| 新增 `conversations`/`messages` | 问答功能的多轮对话历史（已确认支持多轮） |

## 7. 合规与法律风险（大幅收窄后）

由于确定了：香港服务器、邀请码制不对外公开注册、充值走个人转账+人工记账（不接支付网关）、不需要企业资质、不大规模开放——之前最重的几项风险基本都不适用了：

- ~~工商资质~~：不需要，充值不走商户号。
- ~~支付渠道合规（微信支付/支付宝商户号、Stripe）~~：不需要，没有接入任何支付网关。
- ~~ICP 备案~~：不是面向公众经营性提供服务，且部署在香港；只要不做大规模公开推广、不主动面向大陆公众招揽注册，这条基本不适用。个人转账收款本身也有额度和监管上限，运营方需自行留意别做成"看起来像商业经营"的规模。
- ~~生成式 AI 服务备案~~：面向邀请制小范围用户、非公开对外提供，通常不构成"向公众提供生成式 AI 服务"的适用情形；如果规模明显扩大（见 §9 的"不大规模开放"边界），需要重新评估。

仍然值得注意的点：

1. **医疗相关内容红线**：现有产品已有"不做诊疗/剂量建议"的红线设计（`guard.ts`），问答功能开放自由提问后风险敞口更大（用户可能直接问"我这个症状吃什么方子"），红线拦截需要比现在的段级解读更严格——这条和规模大小无关，值得保留。
2. **账号安全与个人信息**：即便是邀请制小圈子，用户名/密码/对话记录也是需要基本保护的个人信息，建议至少做到密码哈希存储、HTTPS 传输、不在日志里记录明文对话内容。
3. **"人工记账充值"的操作规范**：因为没有支付网关兜底对账，管理员手动改余额这个操作本身要有留痕（谁、什么时候、改了多少、备注依据），否则一旦用户对余额有异议（"我明明转了钱""怎么被扣光了"），没有凭证会很被动。
4. **"不大规模开放"的边界要有共识**：现在的合规结论建立在"小范围邀请制"这个前提上，如果后续用户量明显变大、或开始公开对外宣传拉新，§9 里的这些"不适用"判断需要重新评估（尤其是要不要转向企业化运营）。

## 8. 分阶段推进建议（如果决定做）

| 阶段 | 内容 | 备注 |
|---|---|---|
| A. 后端基础设施 | 香港服务器 + PostgreSQL + 基础 REST/tRPC API（对齐现有 30 个 IPC 语义） | 可复用现有 `services/*` 业务逻辑 |
| B. 账号与权限 | 邀请码注册/登录 + 三级权限（游客/免费会员/充值会员，见 §4.1） | 比公开注册体系简单很多，不需要短信/邮箱验证 |
| C. 内容管理后台 | 书/章/段的上传、编辑、发布/下线界面 | 复用 `editing.ts` 的 CRUD 逻辑，改造为管理员后台 |
| D. 前端迁移 | Electron 渲染进程 → 独立 Web 前端，`ipc.ts` 换成 HTTP client | `src/views`/`src/components` 大部分平移；按权限矩阵隐藏/禁用对应功能 |
| E. 问答功能 | RAG 检索增强问答（多轮），接入 token 计量与余额扣减 | 计费模型能否成立的关键模块，见 §4 |
| F. 钱包与人工充值后台 | 余额展示、`balance_adjustments` 记账界面、扣减日志查询 | 不需要支付网关，只是一个管理员操作+审计界面 |
| G. 运营工具 | 邀请码生成/管理、用户列表、异常用量监控/限流 | |
