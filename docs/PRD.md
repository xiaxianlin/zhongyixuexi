## 1. 概述（v4.0 目标形态）

### 1.1 产品定位

一款**部署在香港服务器的邀请制在线中医经典学习站点**，运营方后台统一上传管理《黄帝内经·素问》《黄帝内经·灵枢》《黄帝八十一难经》《伤寒论》《金匮要略》等经典，组织为可阅读、可检索的章节与段落结构，并提供 AI 段级白话解读、AI 问答（多轮对话）、全文检索、段绑定/自由笔记与阅读足迹统计。

产品**不对外公开注册**，仅通过邀请码开放；按三级权限区分能力（游客/免费会员/充值会员，见 §1.2 C-2 与 §3.2）；AI 调用统一走平台侧 Key，问答功能按 token 用量计费，充值走用户个人转账 + 后台人工记账（不接支付网关）。完整论证见 `docs/dev/proposal-online-membership-billing.md`。

> v3.1 及之前的"本地桌面、无账号、无服务端"形态仍是当前已上线代码的真实状态，本节描述的是 Phase 9 完成后的目标形态。

### 1.2 核心约束（v4.0）

| 编号 | 约束 | 说明 |
|---|---|---|
| C-1 | 在线 Web 服务 | 部署在香港服务器的浏览器可访问站点；不做原生移动端 App（响应式适配可选） |
| C-2 | 邀请制、三级权限 | 不开放自主注册，仅邀请码注册；游客（未登录）只读原文，免费会员（邀请码注册）可看 AI 解读，充值会员（钱包余额 > 0）可发起 AI 问答对话，详见 §3.2 |
| C-3 | AI 走平台 Key，问答按 token 计费 | 段级白话解读走全局共享缓存，不单独计费；AI 问答按每次调用的 token 用量从会员钱包余额扣减；不保留用户自带 Key |
| C-4 | 充值走人工记账，不接支付网关 | 用户个人转账给运营方 → 管理员在后台手动为账号加值（记账留痕）；不对接微信支付/支付宝商户号或 Stripe |
| C-5 | 专业学习导向 | 核心 = 阅读 + 理解 + 问答 + 检索 + 笔记 + 足迹，不做社交、裂变、推荐流 |
| C-6 | 内容由后台管理 | 经典内容由运营方通过内容管理后台上传、编辑、发布/下线，不再随应用包分发 |
| C-7 | 不大规模对外开放 | 面向邀请制小范围用户；一旦规模扩大或公开推广，需重新评估 §8 的合规结论（ICP 备案、生成式 AI 服务备案等） |

### 1.3 价值主张

- **开箱即读**：内置多部中医核心经典，邀请码登录即可系统学习。
- **AI 段级解读**：逐段生成白话译文、医理点拨与综合解读，全体会员共享，免费会员即可查看。
- **AI 问答**：充值会员可就经典内容多轮追问，按 token 用量计费。
- **全文检索**：FTS 跨书检索，命中段落可一键定位。
- **段绑定笔记**：阅读时围绕具体段落沉淀心得。
- **阅读足迹**：仪表盘呈现阅读进度、解读覆盖率、笔记量与热力图。
- **轻量可控的计费**：无需绑卡/授权代扣，充值即时到账、余额透明可查。

## 2. 目标用户与场景

### 2.1 用户分层

| 优先级 | 人群 | 核心诉求 |
|---|---|---|
| P0 | 中医院校学生 / 备考者 | 逐段读懂《内经》《难经》原文，理解医理，做笔记沉淀 |
| P1 | 深度爱好者 / 临床进修者 | 系统学习经典，检索主题，对照理解 |
| P2 | 传统文化 / 医史研究者 | 全文检索、引用、定位 |

### 2.2 典型场景

- **S1 逐段精读**：打开《素问》→ 选章 → 选段 → 一键 AI 生成白话/医理/解读 → 三栏对照理解。
- **S2 主题检索**：搜"脾虚" → 跨五书命中段落 → 点击跳转到书籍详情对应段。
- **S3 段落笔记**：读到关键段 → 添加笔记 → 抽屉查看该段所有笔记。
- **S4 足迹回看**：仪表盘查看已读章节数、AI 解读覆盖率、阅读热力图。
- **S5 AI 辅助**：选段 → DeepSeek 生成白话 → 解读面板展示 → 可重新生成（覆盖）。

### 3.2 账号与权限模块（AUTH，新增）

| 编号 | 功能 | 优先级 | 验收标准 |
|---|---|---|---|
| AUTH-01 | 邀请码注册 | P0 | 不开放自主注册；凭有效邀请码 + 设置密码完成注册；邀请码一次性或多次可用由管理员配置 |
| AUTH-02 | 登录/会话 | P0 | 用户名+密码登录，JWT/Session 维持会话 |
| AUTH-03 | 三级权限矩阵 | P0 | 见下表，所有权限判断在后端 API 层强制，前端隐藏仅为体验优化 |
| AUTH-04 | 邀请码管理 | P1 | 管理员可生成/查看/作废邀请码，记录用途备注 |

**三级权限矩阵**（详见 `docs/dev/proposal-online-membership-billing.md` §4.1）：

| 能力 | 游客 | 免费会员 | 充值会员（余额 > 0） |
|---|---|---|---|
| 查看原文 | ✅ | ✅ | ✅ |
| 查看 AI 段级白话解读 | ❌ | ✅ | ✅ |
| 发起 AI 问答/多轮对话 | ❌ | ❌ | ✅（按 token 计量扣余额） |

> 充值会员余额扣至 0 时自动降级为免费会员能力（原文/解读仍可见，问答不可用），不需要额外的"套餐到期"逻辑。

| 编号 | 功能 | 优先级 | 验收标准 |

### 3.8 AI 工具模块（AI）

> AI 调用统一走平台侧 Key（不再保留用户自带 Key）。段级白话解读全体会员共享缓存、不单独计费；AI 问答按 token 用量从充值会员余额扣减，见 §3.2。

| 编号 | 功能 | 优先级 | 验收标准 |
|---|---|---|---|
| AI-01 | 段级白话解读 | P0 | 免费会员起可查看；生成后全局缓存（prompt_hash 命中），全体会员共享同一结果；管理员可重新生成（覆盖 active 版本） |
| AI-02 | 失败降级 | P0 | 调用失败时，解读面板明确提示，不影响阅读 |
| AI-03 | 红线拦截 | P0 | System Prompt 禁止诊疗/剂量建议；输出端关键词兜底净化；**问答功能的红线拦截需比段级解读更严格**（自由提问风险敞口更大） |
| AI-04 | 解读版本化 | P1 | `paragraph_analyses` 持 active 唯一版本；重新生成覆盖 active |
| **AI-05** | **AI 问答（新增）** | **P0** | 充值会员可基于经典内容发起多轮问答；基于全文检索做 RAG（检索相关段落 → 拼接上下文 → 调用平台 Key）；每次调用按返回的 `prompt_tokens+completion_tokens` 记账，从钱包余额实时扣减；余额不足时拒绝调用并提示充值 |

### 3.9 钱包与充值模块（WALLET，新增）

| 编号 | 功能 | 优先级 | 验收标准 |
|---|---|---|---|
| WALLET-01 | 余额展示 | P0 | 会员可查看当前 token 余额与消耗流水 |
| WALLET-02 | 人工充值记账 | P0 | 管理员在后台为指定会员账号手动加值，记录金额、折算 token 额度、备注、操作人、时间；**不对接任何支付网关** |
| WALLET-03 | Token 用量流水 | P0 | 每次问答调用的 token 消耗、扣减后余额、关联会话，可供会员与管理员对账 |

> 定价（每 1000 token 折算多少钱）与免费额度规则待定，见 `proposal-online-membership-billing.md` §9。

### 3.10 学习足迹模块（LRN）

| 编号 | 功能 | 优先级 | 验收标准 |
|---|---|---|---|
| LRN-01 | 阅读足迹仪表盘 | P0 | 展示：书/章/段总数、已 AI 解读段数与覆盖率、笔记数、活跃阅读书数、累计阅读秒数、年度热力图、最近阅读书目（均按 `user_id` 维度统计） |

> 本模块**不包含记忆卡/SM-2/测验**。学习 = 用户的真实阅读/解读/笔记足迹。

## 4. 非功能需求

### 4.1 性能

| 编号 | 指标 | 目标 |
|---|---|---|
| NFR-P1 | 首屏加载 | ≤ 3 秒（不含冷启动概念，改为 Web 首屏） |
| NFR-P2 | 章节/段落打开 | ≤ 300ms |
| NFR-P3 | 全文检索 | ≤ 300ms（千段落级） |
| NFR-P4 | AI 段级解读 | 单段 ≤ 15 秒（含网络） |
| NFR-P5 | AI 问答首字节 | ≤ 3 秒（流式返回可接受更长总时长） |

### 4.2 可靠性与数据安全

- PostgreSQL 事务保护，异常不丢数据；定期备份（服务器侧）。
- 阅读进度与笔记按 `user_id` 隔离自动保存。
- 平台侧 AI Key 存于服务器 Secrets 管理，不落库、不进日志、不下发前端。
- **段落与章节采用稳定 ID**，AI 解读/笔记/进度按段 ID 绑定，不因内容调整失效。
- **人工充值记账**需留痕（操作人、时间、金额、备注），作为余额争议的核对依据。

### 4.3 兼容性

- 主流桌面浏览器（Chrome/Edge/Safari/Firefox 最新两个大版本）；移动端浏览器可用但不专门优化布局。
- 适配常见分辨率（1280 起）与高 DPI / 4K 缩放。
- 依赖网络：所有功能均需在线（内容浏览、AI 解读、AI 问答均经服务器）。

### 4.4 可访问性

- 动态字体大小、完整键盘操作。

## 5. 数据模型（v4.0 目标形态，详见 `proposal-online-membership-billing.md` §6）

### 5.1 内容来源

不再随包分发 JSON 夹具。经典内容由运营方通过内容管理后台（CMS-01）直接写入共享数据库，`docs/dev/book-import-json.md` 描述的导入中间格式可作为后台批量导入的辅助工具保留。

### 5.2 核心表（目标 schema，PostgreSQL）

| 表 | 说明 | 相对 v3.1 的变化 |
|---|---|---|
| `books`/`chapters`/`paragraphs` | 内容主体，全局共享（对所有用户一致） | 新增 `status`（draft/published）、`created_by`；不再有单机 seed 概念 |
| `reading_progress`、`notes` | 阅读进度、笔记 | 新增 `user_id`，改为多用户维度 |
| `ai_cache`、`paragraph_analyses` | AI 解读缓存与版本化 | 保持全局共享设计不变 |
| `users` | 会员账号 | 新增：密码哈希、角色（member/admin）、注册所用邀请码 |
| `invite_codes` | 邀请码 | 新增：code、可用次数、生成人、备注 |
| `wallets` | 会员钱包余额 | 新增 |
| `balance_adjustments` | 人工充值记账 | 新增：金额、折算 token 额度、操作管理员、备注、时间 |
| `token_usage_ledger` | 问答调用 token 用量流水 | 新增：与钱包扣减对应 |
| `conversations`/`messages` | 问答多轮对话历史 | 新增 |
| ~~`api_credentials`~~ | 用户自带 Key | **整表删除**：平台 Key 存服务器 Secrets，不落库 |
| `settings` | KV 设置 | 保留，用于平台级配置 |

> **schema 迁移**：延续 forward-only 迁移原则（不 `DROP`/regenerate 稳定 ID），但迁移 runner 需要从 `better-sqlite3` 换成 PostgreSQL 迁移工具。

## 6. AI 服务设计（v4.0 目标形态）

### 6.1 段级解读（AI-01）

- 输入：段落原文 + 固定 Prompt（中医典籍含医理点拨模板）→ 结构化输出（白话/医理/解读）。
- 温度 0.3，JSON 模式。
- 输出写入 `paragraph_analyses`（active 版本）+ `ai_cache`；**全体会员共享同一结果**，不产生按用户计费的 token 用量。

### 6.2 AI 问答（AI-05，新增）

- 用户提问 → 基于全文检索（SRH）取相关段落 → 拼接上下文交给平台 Key 调用 → 返回答案。
- 支持多轮：同一 `conversation` 内的追问带上历史消息。
- 每次调用按返回的 `prompt_tokens + completion_tokens` 写入 `token_usage_ledger`，从 `wallets` 余额实时扣减；余额不足拒绝调用并提示充值。

### 6.3 缓存与成本

- 段级解读：`ai_cache` 按 `prompt_hash`（归一化 prompt + model + temp 的 sha256）命中，避免重复调用，是运营方的固定 COGS。
- AI 问答：不缓存（每个用户的问题各不相同），是唯一产生按用户计量 token 费用的功能，也是"充值"这件事在产品上的唯一意义。

### 6.4 红线与降级

- System Prompt 显式禁止诊疗/剂量建议。
- 输出端关键词兜底净化（中医剂量正则）。
- **问答功能的红线拦截需比段级解读更严格**：自由提问的风险敞口更大（用户可能直接问症状/处方）。
- 调用失败：解读/问答面板提示，不阻断阅读（AI-02）。

## 7. 技术架构（v4.0 目标形态，详见 `proposal-online-membership-billing.md` §3）

```
    ┌─────────────────────────┐      ┌─────────────────────────────┐
    │  会员端 Web 前端           │      │  运营/内容后台（管理员专用）    │
    │  React + Vite/Next.js    │      │  书/章/段上传编辑、邀请码生成、  │
    │（现有 src/views 大部分迁移）│      │  会员余额人工调整（对账个人转账）│
    └────────────┬─────────────┘      └───────────────┬─────────────┘
                 │ HTTPS / REST or tRPC                │ HTTPS（管理员鉴权）
                 └───────────────┬──────────────────────┘
                        ┌────────▼─────────────┐
                        │        后端 API 服务          │
                        │  Node.js（Nest/Fastify），     │
                        │  部署在香港服务器               │
                        │  - 账号/鉴权（邀请码注册 + JWT）│
                        │  - 三级权限（游客/免费会员/     │
                        │    充值会员）                   │
                        │  - 钱包余额 & token 计量中间件  │
                        │  - 内容服务（books/chapters/   │
                        │    paragraphs，沿用现有逻辑）  │
                        │  - AI 网关（问答/RAG + 段级解读，│
                        │    平台侧 Key，逐调用记账）     │
                        └───────┬───────────┬──────────┘
                                │           │
                    ┌───────────▼───┐   ┌───▼─────────────┐
                    │  PostgreSQL    │   │ 对象存储（封面等）│
                    │ （多用户 schema）│   └─────────────────┘
                    └────────────────┘
```

> 没有支付渠道网关：充值是用户线下个人转账给运营方 → 管理员在后台手动加余额，系统只需一张记账表（`balance_adjustments`），不接 Stripe/微信支付/支付宝。

### 7.1 技术选型（草案）

- **前端**：React + TypeScript + Vite（或 Next.js）；现有 `src/views`/`src/components` 大部分平移，`src/models/shared/ipc.ts` 替换为 HTTP client。
- **后端**：Node.js（Nest/Fastify），部署在香港服务器；现有 `electron/services/*`（`content-normalize.ts`/`paragraph-analysis.ts`/`parse-hash.ts`）与 `electron/ai/*`（`deepseek.ts`/`guard.ts`/`prompts.ts`）业务逻辑可直接迁移复用。
- **存储**：PostgreSQL（替代 better-sqlite3，支持多用户并发写入）；全文检索用 Postgres `tsvector`/`pg_trgm` 或独立搜索服务。
- **鉴权**：邀请码注册 + JWT/Session；不再有"用户自带 AI Key"的 `safeStorage` 加密存储，平台侧 Key 存服务器 Secrets 管理。
- **对象存储**：封面等静态资源迁移到对象存储（如 S3 兼容服务），不再用本地文件系统。

### 7.2 部署与运维

- 部署地域：香港服务器。
- 不接支付网关，因此不需要支付相关的 Webhook/回调基础设施。
- 需要基本的限流/防刷（防止单会员异常刷 token）与监控。

### 7.3 数据与联网

- 内容、进度、笔记、解读缓存均在服务器数据库，不再是"本地优先"。
- AI 调用（段级解读 + 问答）全部经服务器统一走平台侧 Key，不再有"用户自配 Key"的概念。

## 8. 合规与风险（v4.0，详见 `proposal-online-membership-billing.md` §7）

已确认：内容由运营方后台上传管理，无版权问题；香港服务器部署；邀请码制不对外公开注册；充值走个人转账+人工记账（不接支付网关）；不需要企业资质；不大规模对外开放。基于这些前提，工商资质、支付渠道合规、ICP 备案、生成式 AI 服务备案等重负担项**暂不适用**（如后续规模扩大或公开推广，需要重新评估）。

仍需持续关注：

| 风险 | 说明 | 应对 |
|---|---|---|
| 医疗内容合规 | 问答功能开放自由提问后，风险敞口比段级解读更大（用户可能直接问症状/处方） | 定位为阅读/学习工具；不给剂量、不推处方、不做诊疗；问答红线拦截需比段级解读更严格；显著免责声明 |
| 内容准确性 | 古籍文本 + AI 生成未经专家审核 | AI 生成内容标注；免责声明提示用户自行判断 |
| 账号与对话数据保护 | 密码、对话记录属于需要基本保护的个人信息 | 密码哈希存储、HTTPS 传输、日志不记录明文对话内容 |
| 人工充值记账的可核对性 | 没有支付网关兜底对账 | `balance_adjustments` 必须留痕（操作人/时间/金额/备注），便于用户对余额有异议时核查 |
| "不大规模开放"边界 | 当前合规结论建立在小范围邀请制前提上 | 用户量或对外公开程度明显变化时，重新评估本节结论 |
